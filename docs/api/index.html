ForUsBots — API Reference

Docs API Reference Sandbox
openapi.yaml v2.6.0 OAS 3.0

Reference for nine Playwright automation bots, public job polling, durable idempotent scrape submissions, token scopes, and admin runtime controls.
All routes are namespaced under /forusbot. A plain /health also exists.

authentication & scopes

Protected routes accept x-auth-token: YOUR_TOKEN or Authorization: Bearer YOUR_TOKEN. Tokens are loaded from tokens.json (or TOKENS_FILE); a deployment may materialize that file from the TOKENS_JSON secret. There is no shared-token contract.

Roles: admin, user, pa_lead, rm_lead, ops_lead, and imp_lead. Effective scope merges role defaults with token-level deniedFeatures, deniedEndpoints, and allowedEndpoints; an exact allow overrides denies.

/locks, /settings, /metrics, /version, and /openapi require an admin token. Update-plan and users-management additionally enforce email allowlists; an admin token outside the allowlist still receives 403.

runtime bot IDs

Use these exact botId filter values: vault-file-upload, scrape-participant, scrape-plan, search-participants, forusall-mfa-reset, update-participant, update-plan, forusall-emailtrigger, and users-management.

POST /forusbot/sandbox/vault-file-upload Validate headers/body without launching a job

Dry-run validator. Does not require auth. Validates x-filename and parses/validates x-meta. If a binary body is attached, it is counted but not processed. Returns 200 with a normalized echo or 4xx on validation errors.

Parameters (Headers)

Name In Type Req Description
x-filename header string yes Must end with .pdf. This public dry-run is intentionally narrower than the real upload.
x-meta header string (JSON) yes Same shape as upload x-meta.
Content-Type header enum no application/octet-stream or application/pdf if binary body is sent.

POST /forusbot/users-management/create Create portal user (queued, RESTRICTED)

Auth required (x-auth-token) and restricted to ivan.alvis@forusall.com and sponsorservicesbot@forusall.com. Other tokens (incl. admins) receive 403 forbidden. Opens https://employer.forusall.com/users/new, fills the #new_user form top-down, and clicks Create. Success is detected by redirect to /users with #flash_notice containing "User created successfully."; failure is detected by #error_explanation li.

Request Body

{
  "user": {
    "firstName": "Jane",
    "lastName": "Doe",
    "email": "jane.doe@example.com",
    "password": "S3cretPass!",
    "passwordConfirmation": "S3cretPass!",

    "userGroupIds": [1],
    "payrollSetupIds": [230],
    "active": true,

      "payrollTransaction": false,
      "monthlyEligibleParticipants": false
    }

  "includeScreens": false,

Notes

  • role: integer 1..6 (1=forus_admin, 2=sponsor_admin, 3=sponsor_rep, 4=super_admin, 5=cs_admin, 6=auditor).

POST /forusbot/users-management/edit Edit portal user with optional Reset MFA (queued, RESTRICTED)

Auth required (x-auth-token) and restricted to the same allowlist as create. Opens /users/{userId}/edit, applies only the keys present in updates (patch semantics), optionally executes Reset MFA, and clicks Update. Success is detected by redirect to /users with "User updated successfully." in #flash_notice.

Request Body

{
  "userId": 1062,
  "updates": {
    "firstName": "Pension",
    "role": 3,
    "sponsorIds": [515, 221],
    "active": true,
    "notAnEmployee": false
  },
  "resetMfa": "employer",
  "note": "Update role per sponsor request",
  "includeScreens": false,
  "timeoutMs": 30000
}

Notes

  • updates: subset of the create-user fields. password/passwordConfirmation are optional; if one is present, the other must match.
  • resetMfa: "employer", "admin", "both", or "none" (default). When not "none", the bot clicks the corresponding Reset MFA button(s) before the Update submit, accepting both the confirm() and the success alert() dialogs and verifying #mfa_status changes to "not enrolled".
  • If updates is empty AND resetMfa === "none", the request is rejected with 422 ("nothing to do").

Responses

202 Accepted

POST /forusbot/email-trigger Trigger email communications (queued)

Auth required (x-auth-token). Triggers various types of email communications to plan participants. Supports 10 different email types including statements, onboarding, sponsor communications, and generic emails. Always sends to all participants.

Email Types

  • statement_notice - Quarterly statement notifications
  • sponsor_quarterly_email - Sponsor quarterly updates
  • onboard_communications - Onboarding emails
  • new_hire_communications - New hire emails
  • generic_email - Generic communications with custom audience
  • monthly_balance - Monthly balance updates
  • year_end_notice - Year-end notifications
  • notify_auto-escalation - Auto-escalation alerts
  • summary_annual_notice - Annual summary notices
  • force_out - Force out notifications

Accepts a raw binary body with headers carrying metadata. Supported file types: .pdf, .xlsx, .xls, .csv, and .zip. The server logs in (TOTP), fills the form, and processes the job asynchronously. Returns 202 with a jobId and ETA.

Name In Type Req Description

x-filename header string yes Original filename. Must end with .pdf, .xlsx, .xls, .csv, or .zip.

Content-Type header enum yes application/octet-stream, application/pdf, application/vnd.openxmlformats-officedocument.spreadsheetml.sheet (.xlsx), application/vnd.ms-excel (.xls), text/csv, or application/zip.
